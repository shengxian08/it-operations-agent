# T04 显式人工请求与持久上下文

授权来自完整剩余任务目标与已有 T04 验收；按当前工作区顺序实施，不重复申请设计确认。T03 已独立验收。现有持久编号、运行租约、唯一 run_id、审计事务和 pending 语义继续作为基础。

## 业务合同

明确“请转人工/联系人工支持/我要人工客服”等动作直接产生 `explicit_manual_request`，跳过检索、模型、查单和签名工具。安全输入/受限操作检查仍优先；否定、如何转人工的咨询、引号或代码中的请求文字不能误触发。

只有持久化成功后回传记录编号；pending 是待处理，不能宣称人员接单或外部联系已送达。界面保留现有有编号/无编号两种交接结果语义。

新增可空的 `Escalation.context` JSONB。新记录包含 schema_version、captured_at、问题/影响/尝试字段（未知为 null）、字段来源 run/draft/version、最多 5 条当前会话员工原文及其真实 message_id、最多 5 个引用身份。员工原文每条最多 2000 字，过长时保存来源编号及明确省略原因，保留原始消息；仅选择最近 5 条时明确较早消息未纳入。结构化字段只来自最近一轮服务器收集记录或该轮当前草稿，不从 assistant 文本猜测事实，不自动生成摘要。取消及其他意图后不复用更早的结构化故障状态。

引用仅保存实际 document_id/index_revision/chunk_index 和来源 message_id，不保存可永久回放的 title/excerpt。保存和每次读取均核查当前来源 active/权限、原 snapshot 权限及实际 chunk。缺少可靠 revision 或无法访问时不返回引用内容。读取时按当前请求者 enabled 账号及数据库角色，返回可访问来源标题、出处和原 chunk；超过摘要容量的 chunk 明确提示查看原文，不截断条件后冒认完整。模型、任意历史或客户端参数不能注入引用/上下文。

普通 worker 与超时/崩溃恢复共用上下文构建规则。同 run 重试保持首次快照，不覆盖已记录的事实，只一条 escalation 和一条 created audit。旧行 context=null 明确显示“历史记录未保存故障上下文”，不补写猜测快照。上下文构建/落库失败不能产生成功编号；数据库故障保持可追踪失败。

支持端可读取单条明细、有限上下文及按时间排列的处理审计。员工只能查看自己记录，其他员工 404；当前有效 support/admin 可查看与处理。列表不返回未鉴权的引用原文。分派列表和保存动作都复核当前 enabled support/admin；保存保留版本冲突和合法状态迁移。审计记录操作者、时间、版本、状态/责任人 from/to，接口只返回这些业务白名单字段。
