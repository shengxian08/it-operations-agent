# 企业 IT 运维知识助手：MVP 产品设计

**日期：** 2026-08-12

**状态：** 待评审

**目标：** 以可本地运行、可量化验证的完整 Agent 产品作为求职作品集，展示 Agent 编排、RAG、工具治理、人工兜底、评测与可观测能力。

## 1. 产品定位与边界

### 1.1 目标用户与问题

目标用户为企业内部员工。员工在 VPN、账号、权限、办公软件、设备与网络问题出现时，往往需要翻阅零散知识库或向 IT 支持反复描述问题；已有工单的进度也难以快速获知。

产品提供中文对话式 IT 运维支持：优先使用可追溯的知识库证据给出排障建议；必要时查询模拟工单；问题未解决时协助生成工单草稿，由员工明确确认后再提交。证据不足、工具异常、越权或高风险请求均不自动执行，转为人工兜底建议。

### 1.2 首版目标

- 形成“咨询 → 检索解答 → 查询/创建工单 → 人工兜底 → 反馈回流”的可演示闭环。
- 让每次 Agent 执行具备可解释的状态、引用、工具审计和 Trace。
- 使用项目内置的脱敏模拟数据、Mock 模型模式和 Docker Compose，使任何评审者无需 API Key 也能运行与验证。
- 在接入 OpenAI 兼容模型后，以同一接口展示真实模型的问答与工具调用能力。

### 1.3 非目标

以下能力明确不属于 MVP：

- 真实企业 SSO、AD/LDAP、完整 RBAC 和多租户。
- 接入 Jira、ServiceNow 等外部工单系统。
- 自动执行重置密码、修改权限、重启设备等高风险运维操作。
- 复杂计费、运营后台、生产级集群、跨区域容灾和高并发优化。
- 全量 OCR、多模态解析或大规模异构文档治理。

## 2. 用户体验与功能需求

### 2.1 对话工作台

浏览器端提供中文对话界面，支持流式输出。每条回答显示：

- 分步排障建议或明确的无法确认原因。
- 用于回答的知识库来源，包括文档标题、片段和定位信息。
- 进行中的检索或工具调用状态，以及其最终结果的简要说明。
- “已解决”“仍未解决”反馈入口。
- 需要人工支持时的转人工提示，包含已收集的上下文摘要。

首版采用本地模拟用户身份，不实现真实登录；但请求上下文必须携带固定的 `user_id`，使权限过滤、工单归属与审计具备清晰的扩展边界。

### 2.2 Agent 工作流

使用 LangGraph 构建显式状态图，而不是将全部控制权交给自由 ReAct 循环。标准执行路径为：

```text
接收消息
  → 意图识别
  → 检索/查询改写（按需）
  → 混合检索与重排
  → 证据充分性判断
  → 直接回答 | 查询工单 | 收集建单信息 | 转人工
  → （建单）生成结构化草稿
  → 用户确认
  → 提交工单 | 取消/修改草稿
  → 记录反馈、审计与 Trace
```

工作流状态至少包括：`conversation_id`、`user_id`、当前消息、意图、检索结果及分数、引用、工具调用历史、建单草稿、确认状态、最终答复、转人工原因、错误信息和 Trace ID。

安全与可靠性规则：

- 设置最大工作流步数、最大工具调用次数和重复调用检测，避免失控循环。
- 仅 `get_ticket_status` 可在授权范围内自动调用；`create_ticket` 仅在前端显式确认后调用。
- 工具调用必须有 JSON Schema/Pydantic 入参校验、超时、有限重试和幂等键。
- 检索证据不足、引用冲突、连续工具失败、敏感/越权意图或模型不可用时，不生成虚假结论，不执行写操作；给出可解释的转人工建议。
- Mock 与真实模型使用相同的 Provider 抽象；切换仅通过环境变量或配置完成。

### 2.3 RAG 与知识库

内置约 30～50 篇脱敏模拟 IT 运维资料，主题覆盖 VPN、账号、密码与权限、办公软件、设备、网络、安全与常见故障。源格式以 Markdown 为主，并包含少量结构相对简单的 PDF 作为解析验证材料。

索引流水线包含：文档导入、质量校验、文本提取、清洗、按语义/长度分块、Embedding、关键词索引、版本记录和增量更新。每个文档与分块记录来源、更新时间、访问级别和版本。

查询采用“Qdrant 稠密向量 + 应用内 BM25”混合召回，再使用本地轻量 Cross-Encoder 重排器筛选最终上下文。回答必须包含可返回到原始文档片段的引用。首版仅使用模拟访问级别进行过滤，为后续 RBAC 留出接口。

### 2.4 模拟工单工具

系统内置约 100 条模拟历史工单，状态至少包括待处理、处理中、已解决、已关闭，字段包括工单号、创建人、类别、优先级、描述、状态、更新时间和处理记录。

向 Agent 暴露两个受控工具：

| 工具 | 类型 | 行为与约束 |
| --- | --- | --- |
| `get_ticket_status` | 只读 | 根据工单号或当前模拟用户查询其可见工单，返回状态和最新进展；超时、权限不足和不存在均返回可解释结果。 |
| `create_ticket` | 写入 | 只接受通过 Schema 校验的草稿；必须带用户确认令牌与幂等键；成功后返回工单号和状态。 |

创建工单采用两阶段交互。Agent 只能生成标题、类别、优先级、问题描述和已尝试操作组成的草稿；界面展示草稿并允许用户确认、取消或修改。只有确认事件到达后，后端才能调用写入工具。模型不得直接触发写入。

### 2.5 模型模式

系统提供两种模型模式：

- **Mock 模式（默认）**：使用可预测的固定响应/规则化 Provider，能演示工作流分支、引用、工具草稿与故障处理，不需要 Key，不将其质量作为真实 LLM 能力的结论。
- **真实模型模式**：通过 OpenAI 兼容 API 接入模型。供应商地址、模型名和 API Key 由环境变量配置；记录模型、Token、TTFT、总耗时和错误类别，但不把 Key 或原始敏感提示词写入日志。

## 3. 技术架构

### 3.1 组件划分

| 组件 | 职责 | 主要依赖 |
| --- | --- | --- |
| Web 前端 | 对话、流式展示、引用查看、草稿确认、过程与反馈展示 | React/TypeScript、SSE 客户端 |
| API 服务 | 会话 API、SSE、鉴权上下文、索引/评测管理接口 | Python、FastAPI、Pydantic |
| Agent 服务 | LangGraph 状态机、路由、提示词、工具调度与安全闸门 | LangGraph、模型 Provider 抽象 |
| RAG 服务 | 文档解析、分块、索引、混合检索、重排与引用组装 | Qdrant、应用内 BM25、Embedding、轻量 Cross-Encoder |
| 工单服务 | 模拟工单存储、只读查询、确认后建单与审计 | PostgreSQL、Pydantic Schema |
| 状态与缓存 | 会话短期状态、限流计数、热点检索缓存 | Redis |
| 可观测与评测 | Trace、结构化日志、指标、评测执行与报告 | OpenTelemetry、SQLite/PostgreSQL、评测脚本 |

首版使用 Docker Compose 启动前端、API、PostgreSQL、Redis 与 Qdrant。由于首版仅有 30～50 篇资料，关键词召回由 API 内的 BM25 索引完成，避免引入 Elasticsearch；稠密检索由 Qdrant 完成，二者按固定归一化与加权规则合并后再送入轻量 Cross-Encoder 重排器。

### 3.2 数据流

```text
员工浏览器
  → FastAPI 会话接口（生成 Trace ID）
  → LangGraph 工作流
  → 模型 Provider / RAG 检索器 / 工单工具
  → PostgreSQL、Redis、Qdrant 向量索引与应用内 BM25
  → SSE 返回答案、来源、草稿与过程状态

同一 Trace 关联模型调用、检索分块、工具调用、确认事件、延迟、Token 与失败原因。
```

### 3.3 核心数据对象

| 对象 | 关键字段 | 关系 |
| --- | --- | --- |
| `User` | `id`、显示名、模拟访问级别 | 拥有多个会话和工单 |
| `Conversation` | `id`、`user_id`、状态、摘要、创建/更新时间 | 包含多条消息和多次 Agent Run |
| `Message` | 角色、内容、引用、用户反馈 | 属于一个会话，关联一次运行结果 |
| `AgentRun` | 状态、意图、节点历史、Trace ID、耗时、Token、失败原因 | 关联消息、检索和工具审计 |
| `KnowledgeDocument` / `Chunk` | 来源、版本、访问级别、文本、向量、关键词索引 | 一个文档含多个分块 |
| `Ticket` | 号码、用户、类别、优先级、描述、状态、时间线 | 由确认后的建单请求创建 |
| `ToolAudit` | 工具名、脱敏入参摘要、结果、确认令牌、幂等键 | 关联 Agent Run 和 Ticket |

## 4. 质量、可靠性与安全要求

### 4.1 验收指标

以下指标属于 MVP 作品集的初版目标，全部使用项目内的固定评测集、模拟数据或本地压测口径验证：

| 维度 | 目标 | 证据 |
| --- | --- | --- |
| 检索质量 | Recall@5 ≥ 0.80；引用正确率 ≥ 0.85 | 离线标注评测与报告 |
| 回答质量 | 有答案用例的人工/规则综合通过率 ≥ 0.80 | 评测集自动判定 + 抽样复核 |
| 安全性 | 100% 建单操作经显式确认；无答案/高风险请求不虚构、不写入 | 工作流与集成测试 |
| 工具可靠性 | 模拟工具成功率 ≥ 0.95；失败均可解释并可转人工 | 故障注入、Trace 检查 |
| Mock 体验性能 | 端到端 P95 < 2 秒 | 本地压测脚本 |
| 真实模型体验 | 记录 TTFT、端到端 P95、Token 与错误率 | 观测面板/导出报告，不承诺与外部模型有关的固定时延 |
| 可复现性 | 新环境按文档可启动，种子数据和评测可重复执行 | Docker Compose 冒烟测试 |

评测集包含约 80～120 条用例，覆盖：普通知识问答、需引用回答、歧义问题、无答案问题、已有工单查询、需要建单的问题、取消/修改草稿、工具失败、越权/高风险请求。每条用例记录预期引用、预期工具行为与可接受的最终状态。

### 4.2 可观测性与隐私

- 所有入站请求创建 Trace ID，并传递到 Agent 节点、检索、模型 Provider 和工具调用。
- 至少记录：节点耗时、检索候选与最终引用标识、模型与 Token 用量、工具名及结果类别、确认状态、错误类型和转人工原因。
- 日志不记录 API Key；工具审计仅保存脱敏的入参摘要；模拟数据不得包含真实个人或企业敏感信息。
- 建立 bad case 记录：错误回答、证据不足、用户“仍未解决”反馈、工具失败均可进入评测候选队列。

## 5. 测试策略

- **单元测试**：状态路由、安全闸门、Schema 校验、权限过滤、引用组装、幂等行为、Mock Provider。
- **集成测试**：对话到检索、工单查询、草稿生成/确认提交、工具失败降级、SSE 事件顺序。
- **评测测试**：固定评测集计算检索和回答指标，并保留结果快照以发现回归。
- **端到端测试**：Docker Compose 环境中完成至少一条“知识解答”、一条“查单”和一条“确认建单”路径。
- **故障注入**：模拟模型超时、工具 5xx、Redis 不可用、无检索结果和重复确认，验证系统不误写入并给出合理降级。

## 6. 作品集交付物

- 可本地启动的前端、后端和依赖服务。
- 项目内置模拟知识库、工单种子数据、评测集与初始化脚本。
- README：架构图、启动说明、模型配置、演示脚本、指标口径和已知限制。
- 一份离线评测报告与若干 Trace 示例。
- 录屏可演示三条主路径：带引用的知识解答、工单状态查询、需确认的工单创建。

## 7. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 外部模型无 Key、限流或不稳定 | 默认 Mock 模式；真实模型可选接入；Provider 统一错误分类与降级。 |
| 模拟数据过少导致 RAG 指标失真 | 用主题均衡的资料与标注评测集；明确指标仅代表该固定集；记录 bad case。 |
| Agent 自由规划导致流程不可控 | 采用显式 LangGraph 节点、最大步骤、工具次数限制与确认状态机。 |
| 模型直接触发写操作 | 将写入工具置于服务端确认闸门之后，确认令牌和幂等键为必填项。 |
| 范围膨胀 | 严格遵守“首版必须交付/明确延后”清单；先完成三条主路径再扩展。 |
